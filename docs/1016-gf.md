# `1016-gf`: GF prior

This branch, based on `1015-stable`, speeds up the GF prior of the Flash route.
Tables, cutoffs, grids, the order policy of the onsite XC and the models are
unchanged. Every structure gets the same block keys and the same onsite
quadrature orders as on `1015-stable`. The blocks differ only by summation
order, plus the FP32 sum of far-neighbour densities described below
(at most 1e-8 eV).

## Onsite XC

The order policy evaluates every atom on the medium and fine grids. An atom
uses medium when the two differ by less than 1 meV, otherwise fine and higher
orders. Two options of `OnsiteXC` change how much is computed, not the result.
Both are on by default and reachable as `GFPrior(...).onsite.screen` and
`.onsite.mixed`.

| Option | Effect |
| --- | --- |
| `screen` | The medium/fine difference is first evaluated with only the neighbours within rc + 3 bohr of the atom, by a separate kernel that works entirely in FP32 (grid points, neighbour rows, densities and v_xc). Atoms below 0.5 meV, half the threshold, take medium without the fine grid; every other atom goes through the full policy. The fine/finer step of fine atoms is screened the same way. On 48 structures (2,651 atoms) the full difference was 0.62–1.07 times the near-neighbour one; on 147 structures (12,923 atoms: crystals, disordered, molecular, layered and heavy-element cells, and cells strained by ±5 %) no order decision changed. |
| `mixed` | Neighbours at least 6 bohr from every point of an angular tile are summed in FP32 from FP32 copies of the same splines. Near neighbours, the total density and v_xc stay FP64. The onsite blocks move by at most 1.0e-8 eV on the same 147 structures. |

## Kernels

| Step | Implementation |
| --- | --- |
| Radial tables | One row-tiled Triton kernel for every table. Two-centre blocks are diagonal in m in the bond frame, so each row of C D_R^T has one channel per column: BR products and a rank-1 update per row. Tiles of 8 rows; each program takes 2 consecutive tiles of one displacement (4 in calls of at least 2^15 displacements), so the coefficients of its knot interval are fetched once. Outputs whose blocks all fill the padded shape are not zero-filled first. Tables off the m-diagonal fall back to the per-degree path. |
| Onsite order screen | its own FP32 Triton kernel (8 × 16 angular tile); the output kernel keeps FP64 near neighbours and v_xc |
| Rotation packs | One program per pack row (l, m): the harmonics of each collocation direction are formed once for all columns; D^l only up to the degrees of the tables evaluated on each displacement set |
| Periodic pairs | one Triton kernel (count, prefix sum, write); the translation box is the ceiling of span + reach × dual norm per axis (5³ instead of 7³ translations in large cells); small cells split their candidate translations over programs; one search serves the support and the centre queries |
| Three-centre terms | query pairs, block-key lookup and filters in one Triton kernel per chunk of centres |
| Three-centre sums | FP64 tensor cores (`mma.sync.m8n8k4.f64`), accumulated in registers (`dptb.prior.gf.dmma`). With 4,096 blocks or more, one thread block sums a block and writes it once. With fewer blocks (small cells, hundreds of terms per block) the terms of a block are split over up to 16 thread blocks, and a second kernel adds the partial blocks in a fixed order, so the result stays deterministic |
| Environment XC | PZ81 in one Triton kernel, evaluated per shell pair and broadcast |
| Output | Hermitisation, scalar block, spin layout and gauge permutation in one kernel over 8-row chunks; the reverse block is read in its own row order (coalesced) and transposed on chip |

### Three-centre sums on tensor cores

`dptb.prior.gf.dmma` is a small CUDA extension that
`torch.utils.cpp_extension` compiles on first use.

| Setting | Value |
| --- | --- |
| CUDA toolkit | `nvcc` matching the CUDA major version of the PyTorch build (`CUDA_HOME`), host compiler `CXX`; sm_80 or newer |
| `DPTB_PRIOR_BUILD_DIR` | persistent build directory (default: the torch extensions directory). The first process compiles it, in about 80 s; processes that start together compile it once, because of the build lock, and later processes load it. |
| `DPTB_PRIOR_DMMA=0` | use the Triton kernel instead |

The prior falls back to the Triton kernel when no toolkit is available. Only
the summation order differs, at rounding level.

The H0 prior and UniTB columns come from a separate process that runs only
UniTB on this branch; its H0 prior changed only in the pair search and is within
1.9 % of `1015-stable` on the same card. GF / H0 1015 divides by the `1015-stable`
H0 of the same card. The H0 prior varies by 10–20 % between cards (FFT and
PBE), so ratios are only compared within one card. On the Flash route the heads
now take most of the time at every size: 0.12 s at 16 atoms, 0.34 s at 1,024
atoms.

Throughput with four processes under MPS on one card: Flash 30,973 structures
per hour on a 16–432-atom mix and 12,553 per hour on 40 distinct compositions
(28–288 atoms), each seen for the first time. On the same sets, `1015-stable`
gave 15,735 and 9,492.

The prior is not bit-reproducible from call to call: some accumulating
scatter operations in PyTorch add in a nondeterministic order, which moves some
H blocks in the last bits (at most about 3e-17 eV); S is exact. With
`torch.use_deterministic_algorithms(True)` repeated calls agree bit for bit, at a
cost of 11–17 % in prior time.
